Part I — KLIQ Control System

Overview, modules, analytics, and admin capabilities

1. What is the KLIQ Control System?

The KLIQ Control System is the internal administrative dashboard for the KLIQ social media platform. It is a standalone web application running separately from the consumer-facing KLIQ app (prot_3, port 5173), accessible only to authorised administrators at localhost:5174 in development, and behind a VPN-gated domain in production.

Its purpose is to give administrators full visibility and control over the platform — from user management and content moderation to real-time analytics, community oversight, push notification management, system settings, and direct communication with users. Every meaningful admin action is logged in the Activity Log for auditability.

ℹ️

Design Philosophy

The Control System is built to the same visual quality as the consumer app — dark slate palette with KLIQ cyan/purple/pink brand accents — so that internal tooling feels first-class, not an afterthought. Every table, chart, and modal is purpose-built for the admin workflow.

4. Admin Modules — Detailed Breakdown

4.1 Dashboard

The Dashboard is the landing page. It displays six real-time KPI cards, each acting as a drill-down button. Clicking a card opens a modal with a more detailed breakdown, including a chart and key sub-metrics.

  • KPI Cards: Total Users · Daily Active Users · Content Pieces Today · Revenue MTD · Moderation Queue · Platform Health Score
  • Drill-down modals: Each card maps to a DRILLDOWN config object that specifies the modal title, subtitle, metrics array, and chart type (pie or bar)
  • Quick action panel: Direct links to moderation queue, user management, and push notifications

4.2 User Management

The Users page provides a full table of all registered users with search, filter, and inline moderation actions.

  • Table columns: Avatar, Username, Email, Tier (two-line badge: Tier N + label), Status, Posts, Followers, Joined date, Actions
  • Filters: Full-text search (username, name, email) · Status filter (All / Active / Suspended / Banned / Pending)
  • Actions per user: View Profile (opens prot_3), Verify, Suspend, Reinstate, Ban, Delete
  • Confirmation modal: All destructive actions require a confirm step before execution
  • Tier system: Tier 1 (Basic) · Tier 2 (Plus) · Tier 3 (Pro) — colour-coded with distinct badge styling

4.3 Content Moderation

The Content page surfaces flagged posts and queued reports for admin review, with accept/reject/escalate controls.

4.4 Communities

Overview of all KLIQ communities — member counts, activity scores, flagged communities, and admin tools to merge, archive, or feature communities.

4.5 Messages (Admin Chat)

A WhatsApp-style split-panel chat system allowing admins to communicate directly with users for support, warnings, or follow-up on reported content.

  • Left panel: Conversation list with avatar, username, last message preview, unread badge, online indicator
  • Right panel: Chat bubbles (admin = indigo right, user = slate left), auto-scroll, message timestamps
  • Read receipts: Single tick (sent) → double tick (delivered) → filled double tick (seen)
  • Per-conversation actions: View user profile in KLIQ app, Flag account, Ban user, additional options
  • Seeded conversations: 8 real support scenarios (appeal reviews, ban queries, verification requests)

4.6 Notifications

Push notification management panel. Admins can compose and broadcast notifications to all users, specific tiers, or individual users. Includes delivery tracking.

4.7 App Settings

Platform-wide configuration: feature flags, content policies, rate limits, onboarding flow toggles, maintenance mode, and API key management.

4.8 Admin Profile

Personal admin account management: edit display name, email, and bio; toggle 2FA; change password; sign out with confirmation modal.

4.9 Preferences

Admin-specific settings: email notification toggles (5 categories), real-time alert toggles (4 types), timezone selector (defaults to UTC+2 Namibia), dashboard refresh interval.

4.10 Activity Log

Full audit trail of all admin actions, searchable and filterable by action type.

  • Log entry fields: Timestamp · Action · Target · Type · IP Address · Result
  • Action types: Moderation · User Management · Content · System · Notification
  • 15 seeded entries demonstrate realistic admin workflows

4.11 Header — Global Controls

  • Global search: Search bar for users, content, and communities
  • Notification bell: Dropdown panel with 7 categorised admin alerts (flag, alert, user, growth, safety types), unread count badge, mark-all-read, dismiss individual
  • Admin dropdown: Profile → /profile · Preferences → /preferences · Activity Log → /activity-log · Sign Out → /login
  • View KLIQ App button: Opens localhost:5173 in new tab with KLIQ brand gradient

6. Security Model

  • Authentication: Email + password login at /login. In production: JWT access tokens (15-min expiry) + HTTP-only refresh tokens (7-day).
  • Route protection: All routes under the Layout shell require a valid session. Unauthenticated requests redirect to /login.
  • 2FA: TOTP-based two-factor authentication toggle in Admin Profile. Mandatory for all Production admins.
  • Audit trail: Every write action (ban, delete, modify settings) is logged to the Activity Log with IP address and timestamp.
  • Role separation: In production, extend to: Super Admin · Moderator · Read-Only Analyst. Currently single-role prototype.
  • Network isolation: The Control System should be served on a separate subdomain (admin.kliq.app) behind a VPN or IP allowlist — never on the same origin as the consumer app.

8.3 Connection Pooling

At 10,000 users and 2 API servers, use PgBouncer in transaction-pooling mode. Configure:

max_client_conn = 200          # Max connections from app servers
default_pool_size = 20         # Connections per pool to PostgreSQL
pool_mode = transaction          # Most efficient for web APIs
server_idle_timeout = 600       # Close idle server connections after 10min

9. API & Backend Services

9.1 Recommended Runtime

Node.js 20 LTS with Fastify (or Express) as the HTTP framework. Fastify handles ~70,000 req/sec on a 2-core server — massively above our 10K user needs.

upstream kliq_api {
    least_conn;

9.4 Background Job Queue

Use BullMQ (Redis-backed) for async work. Jobs that must NOT block the request/response cycle:

  • send-push-notification — FCM/APNs delivery, retry on failure
  • process-media-upload — Thumbnail generation, video transcoding (ffmpeg), CDN upload
  • send-email — Verification emails, password reset, admin alerts via SMTP
  • compute-feed — Rebuild personalised feed cache for newly active users
  • generate-analytics-snapshot — Hourly aggregation for the analytics dashboard
  • run-fake-account-detection — Pattern analysis on new registrations

10. Media & CDN Strategy

10.1 Upload Flow

1. Client requests a pre-signed upload URL from API
   POST /api/upload/sign → returns { uploadUrl, fileKey }

2. Client uploads directly to Cloudflare R2 (bypasses API server)
   PUT {uploadUrl} with binary file

3. Client notifies API that upload is complete
   POST /api/upload/confirm { fileKey }

4. API queues background job: process-media-upload
   → Generate thumbnails (400×400, 800×800)
   → Transcode video to HLS (720p, 480p, 360p)
   → Store processed files in R2 under /processed/{fileKey}/
   → Update media_files record: status = "ready", cdn_url = "..."

12.3 Database Query Optimisation (Key Rules)

  • Never paginate with OFFSET on large tables — use cursor-based pagination (WHERE id < :cursor)
  • Index every foreign key and every column used in WHERE clauses or ORDER BY
  • Cache the user feed in Redis with a 5-minute TTL — the feed query is the most expensive single operation
  • Use EXPLAIN ANALYZE on any query over 100ms in staging before deploying
  • Partition the notifications table by month to keep queries fast as row count grows
  • Archive old data — posts >2 years, soft-deleted content, and expired sessions should move to cold storage monthly

14. Security & Compliance

14.1 Application Security

  • Authentication: Bcrypt password hashing (cost factor 12) · JWT RS256 signed tokens · HTTP-only refresh token cookies
  • SQL Injection: Use parameterised queries exclusively (never string interpolation). Use an ORM (Prisma/Drizzle) that enforces this.
  • XSS: Sanitise all user-generated content with DOMPurify before rendering. Content Security Policy headers on all responses.
  • CORS: Allowlist only kliq.app and admin.kliq.app origins. Never *.
  • Rate limiting: As per Section 9.3 — prevents brute force and abuse.
  • File uploads: Validate MIME type server-side (not just file extension). Use magic bytes check. Never execute uploaded files.
  • Secrets management: All secrets in environment variables. Never hardcoded. Use DigitalOcean Secrets or HashiCorp Vault.

14.2 Network Security

  • Admin panel (admin.kliq.app): Restricted to VPN-only access via IP allowlist in Cloudflare. Not publicly reachable.
  • Database: PostgreSQL and Redis are on a private VPC network — no public IP. Only API servers can connect.
  • TLS everywhere: TLS 1.2+ on all connections (client ↔ Cloudflare, Cloudflare ↔ origin, internal services).
  • SSH keys only: No password-based SSH. Ed25519 keys. Disable root login. Non-standard SSH port optional.
  • Firewall rules: Only ports 80, 443 open publicly. All other ports blocked. Internal communication on private VPC.

14.3 Data Privacy & Namibian Compliance

  • Comply with the Namibia Communications Act (Act 8 of 2009) on data handling and user consent.
  • User data should be stored in-region (Johannesburg is acceptable; EU servers may trigger GDPR-like obligations if EU users join).
  • Provide users a data export mechanism (GDPR-equivalent best practice).
  • Retain logs for 90 days for fraud investigation; purge after unless legally required to retain longer.
  • Privacy Policy and Terms of Service must be displayed and accepted at registration.

15.2 Recovery Time Objectives

API Server Failure

RTO: < 2 min

Load balancer automatically routes traffic to remaining server. New server can be provisioned in ~5 minutes from snapshot.

Database Failure

RTO: < 30 min

Managed DB standby promotes automatically. Point-in-time recovery possible within 30 minutes to any point in the last 7 days.

Full Datacenter Outage

RTO: < 4 hours

Restore from daily DB backup to secondary datacenter. DNS failover via Cloudflare. RPO (data loss): max 24 hours.

15.3 Incident Response Steps

  1. PagerDuty / UptimeRobot alert fires → on-call admin notified via SMS within 1 minute.
  2. Check Grafana dashboard for the failing service. Identify: API, DB, Redis, or CDN?
  3. If API server: SSH in, check journalctl -u kliq-api --since "10 min ago". Restart service or redirect load balancer.
  4. If database: Check DigitalOcean console for failover status. Trigger standby promotion if not automatic.
  5. If external service (FCM, Cloudflare): Post status update. Queue jobs will retry automatically on recovery.
  6. Post-incident: Write a blameless post-mortem within 48 hours. Update runbook with new learnings.
